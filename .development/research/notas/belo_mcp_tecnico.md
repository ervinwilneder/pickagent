# belo MCP (Agentic Banking) y el panorama técnico de los MCP fintech — dossier técnico (al 2026-10-28)

Convención de este documento: cada hallazgo se marca con su origen.
- **[SONDEO]** = verificado por mí el 2026-10-28 con curl desde la Mac de Ervin (Cloudflare PoP `SCL`, es decir, no desde una IP de nube).

## Pregunta 1: ¿Hay documentación pública del MCP o de la API B2B de belo? ¿Cómo son los endpoints/tools? ¿Qué son "end-users" y "bifrost"?

### Takeaway
No existe documentación pública del MCP ni de la API B2B de belo: lo único público es la metadata OAuth que el propio servidor expone (RFC 9728 / RFC 8414), la landing `agentic.belo.app`, el hilo de lanzamiento de Manuel Beaudroit en X y notas de prensa. Los nombres de tools reales no se pueden conocer sin autenticarse; sí se conocen los 16 scopes, y `agentic.belo.app` publica una lista de 8 "servicios" V1 con nombres tipo `account.balances` que probablemente no coincidan 1:1 con los nombres de tools MCP.

### Inferences
- El host `b2b.belo.app` y los scopes `end-users:read/write` indican que el MCP está montado sobre la API B2B ("belo Business"): el modelo de datos tiene un "cliente empresa" que puede tener "end-users" (cuentas de usuarios finales administradas por la empresa, típico de embedded finance). Para una cuenta personal esos scopes probablemente no apliquen (igual que `cards:*` "no disponible para cuentas personales" según la guía del hackathon citada por el solicitante). Esto es inferencia: no hay doc pública que defina "end-users".
- "bifrost" es el nombre del authorization server (issuer) y sigue un patrón de nombres nórdicos interno de belo (`baldr.belo.app` aparece en el bundle de docs.belo.app). Bifrost en la mitología nórdica es el puente arcoíris entre mundos: encaja con un servicio de identidad/puente OAuth. Inferencia por nombre; no hay fuente que lo explique.
- Los 16 scopes mapean bien a los 8 "servicios" marketing: `account:read`+`transactions:read`+`deposits:read`+`vaults:read`+`contacts:read` ↔ "Consultar"; `transfers:initiate`+`swaps:execute`+`payments:write`+`pix:write`+`cards:write` ↔ "Operar con tu cuenta". El consent screen "Consultar / Operar" descrito en la guía del hackathon es, casi seguro, un down-scoping del set completo que pide el cliente (ver pregunta 3: Claude pide todos los `scopes_supported` cuando el 401 no trae `scope=`).
- La metadata OAuth cumple el spec MCP 2025-06-18 (RFC 9728 + RFC 8414 + DCR + PKCE S256 + cliente público) pero no las novedades de 2025-11-25/2026-07-28 (sin CIMD, sin `iss` anunciado, sin OpenID discovery). Clientes como Claude Code, Cursor, Codex o el SDK oficial caen en DCR, que funciona.
- Los T&C hablan de un Sandbox "con fondos y datos ficticios". No sé si el sandbox vive en el mismo `b2b.belo.app/mcp` con cuentas de prueba o en otro host; el solicitante indica que el login es con cuenta de Google y que las operaciones reales requieren link de aprobación, lo que sugiere que el mismo endpoint sirve cuentas reales (early access) y que el sandbox del hackathon es una variante por cuenta/tenant.
- El "bloqueo de requests desde servidores cloud durante el hackathon" (dato del solicitante) no afectó mis sondeos de metadata/registro desde una IP residencial chilena (cf-ray SCL). Si existe geofencing/ASN-blocking, probablemente se aplica en `/mcp` o en `/oauth/authorize|token` vía reglas de Cloudflare, no en los `.well-known`.

### Gaps
- Nombres, parámetros y anotaciones de las tools MCP reales: requieren un token válido (login con cuenta belo). No se pudo listar `tools/list`.
- Guía del hackathon ("Consultar"/"Operar con tu cuenta", link que expira en 15 minutos, cotización + aprobación): no la encontré publicada en ningún URL indexado; búsquedas con esas frases no devuelven nada de belo. Es material privado del evento.
- Significado oficial de "end-users" y de "bifrost": sin fuente.
- Documentación de la API B2B subyacente (OpenAPI, paths REST, webhooks): inexistente en público.
- Formato interno del access token (claims, `aud`, vida útil) y si bifrost rota refresh tokens: desconocido (solo se sabe que la firma es EdDSA/Ed25519).

## Pregunta 2: El patrón "cotizar y luego aprobar por link" y cómo se compara con otros diseños human-in-the-loop

### Takeaway
belo usa un patrón "intent → cotización → aprobación fuera de banda por link con vencimiento" que es casi idéntico al de Stripe MCP (confirmación por URL con token de aprobación, 24 h) y al de Mercury MCP (el agente crea un *request* y una persona lo aprueba en la app); difiere de los modelos de "mandato firmado por adelantado" (AP2, Shared Payment Tokens de Stripe/ACP, Agentic Tokens de Mastercard/Visa) donde la persona preautoriza límites y el agente ejecuta sin volver a preguntar, y de x402 (pago máquina-a-máquina sin humano).

- Taxonomía útil para el informe: (a) **aprobación por operación, fuera de banda** (belo, Stripe MCP para writes sensibles, Mercury, Slash): el agente nunca tiene poder de ejecución; el token OAuth solo "propone". (b) **mandato preautorizado con límites** (AP2 Payment Mandate, SPT con `max_amount`/`expires_at`, Agentic Tokens): el humano firma límites antes y el agente ejecuta dentro de ellos. (c) **autónomo máquina-a-máquina** (x402, MPP, Coinbase Payments MCP con límites por llamada/sesión). belo hoy está solo en (a); su roadmap ("Set card limits", "Choose agent permissions") lo mueve hacia (b).
- La diferencia práctica de belo vs Stripe: Stripe usa 24 h de vencimiento y devuelve un *approval token* al agente para reintentar; belo (según la guía citada por el solicitante) usa 15 minutos y un link; ambos obligan al agente a reintentar/consultar estado después del click. Para un agente por WhatsApp/Telegram, 15 minutos es un plazo corto: hay que mandar el link en el mismo turno en que se cotiza.
- Ninguno de los esquemas de redes (Visa TAP, Mastercard Agent Pay, AP2) resuelve el caso belo (cuenta de wallet/cripto/CVU), porque son esquemas de tarjeta/checkout; el comparable directo de belo son Mercury, Slash, Coinbase Payments MCP y Griffin/Nymbus en core banking.

## Pregunta 3: Detalles del spec MCP relevantes (Streamable HTTP, OAuth 2.1, RFC 9728/8414/7591, revisión de junio 2025, SEP-2352, elicitation, tool annotations) y soporte en clientes

### Takeaway
belo implementa exactamente el perfil de autorización de MCP 2025-06-18 (401 + RFC 9728 → RFC 8414 → DCR RFC 7591 → PKCE S256 → cliente público); las revisiones 2025-11-25 y 2026-07-28 agregan CIMD, `iss` (RFC 9207), aislamiento de credenciales por issuer (SEP-2352), step-up de scopes y elicitation en modo URL, nada de lo cual belo anuncia pero tampoco rompe compatibilidad. Claude Code, claude.ai/Desktop, Cursor, Codex/ChatGPT y los SDK oficiales soportan DCR y por lo tanto pueden conectarse a belo sin client id.

### Cited Findings
**Versiones del spec:** existen `2024-11-05`, `2025-03-26`, `2025-06-18`, `2025-11-25`, `2026-07-28` y `draft`. — [DOC] https://modelcontextprotocol.io/llms.txt

**Autorización 2025-06-18 (la que belo cumple):**
- "MCP servers MUST implement OAuth 2.0 Protected Resource Metadata (RFC9728) ... MUST use the HTTP header WWW-Authenticate when returning a 401 ... MCP clients MUST use the OAuth 2.0 Authorization Server Metadata [RFC8414]"; "Authorization servers and MCP clients SHOULD support ... Dynamic Client Registration [RFC7591]"; "MCP clients MUST implement Resource Indicators ... RFC 8707 ... MUST be included in both authorization requests and token requests"; "MCP servers MUST validate that access tokens were issued specifically for them as the intended audience"; "MCP clients MUST implement PKCE"; "All redirect URIs MUST be either localhost or use HTTPS"; tokens nunca en query string; 401 token inválido, 403 scopes insuficientes. — [DOC] https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization
- Esta revisión "removed [the fallback endpoints /authorize, /token, /register] in favor of mandatory RFC 9728 (Protected Resource Metadata)" y hizo obligatorio RFC 8707. — [PRENSA/análisis] https://aaronparecki.com/2025/06/18/10/mcp-spec ; https://www.permit.io/blog/oauth-on-mcp

**Transporte Streamable HTTP (2025-06-18):** un único endpoint que acepta POST y GET; el cliente envía `Accept: application/json, text/event-stream`; el servidor responde JSON o abre un stream SSE; `Mcp-Session-Id` opcional asignado en `InitializeResult` y obligatorio después (400 si falta, 404 si expiró); `MCP-Protocol-Version` header obligatorio en requests posteriores; resumabilidad con `Last-Event-ID`; "Servers MUST validate the Origin header ... to prevent DNS rebinding"; HTTP+SSE viejo deprecado. — [DOC] https://modelcontextprotocol.io/specification/2025-06-18/basic/transports

**Revisión 2025-11-25:** OpenID Connect Discovery como alternativa a RFC 8414 (PR #797); scope incremental vía `WWW-Authenticate` (SEP-835); CIMD como mecanismo recomendado de registro (SEP-991); elicitation en modo URL (SEP-1036); enums mejorados en elicitation (SEP-1330); tasks experimentales (SEP-1686); `WWW-Authenticate` opcional con fallback a `.well-known` (SEP-985); 403 para Origin inválido; SEP-990 (controles de política del IdP empresarial) aparece en el índice de SEPs. — [DOC] https://modelcontextprotocol.io/specification/2025-11-25/changelog ; https://modelcontextprotocol.io/seps/990-enable-enterprise-idp-policy-controls-during-mcp-o

**Revisión 2026-07-28 (la vigente):**
- Autorización: "Authorization servers SHOULD include the iss parameter in authorization responses per RFC 9207, and MCP clients MUST validate a present iss against the recorded issuer before redeeming the authorization code (SEP-2468)"; "Require MCP clients to specify an appropriate application_type during Dynamic Client Registration (SEP-837)"; "**client credentials are bound to the authorization server that issued them: clients MUST key persisted credentials by the issuer identifier, MUST NOT reuse them with a different authorization server, and MUST re-register when the authorization server changes (SEP-2352)**"; DCR queda **deprecado** a favor de CIMD (PR #2858), con ventana mínima de 12 meses. — [DOC] https://modelcontextprotocol.io/specification/2026-07-28/changelog
- Cambios estructurales de 2026-07-28: se elimina `Mcp-Session-Id` y las sesiones a nivel protocolo (SEP-2567); se elimina el handshake `initialize` (cada request lleva versión y capacidades en `_meta`, SEP-2575); nuevo `server/discover`; `subscriptions/listen` reemplaza al GET; se elimina la resumabilidad SSE; patrón MRTR (Multi Round-Trip Requests, SEP-2322) reemplaza las requests iniciadas por el servidor como `elicitation/create` (el servidor devuelve `resultType: "input_required"` y el cliente reintenta con `inputResponses`); tasks pasan a extensión; Roots/Sampling/Logging deprecados; headers `Mcp-Method`/`Mcp-Name` obligatorios en POST (SEP-2243). — [DOC] https://modelcontextprotocol.io/specification/2026-07-28/changelog
- Texto del draft actual sobre scopes y step-up: "MCP servers SHOULD include a scope parameter in the WWW-Authenticate header"; prioridad del cliente: 1) `scope` del 401, 2) todos los `scopes_supported` del PRM; 403 `insufficient_scope` con `scope="..."` para step-up; "MCP Servers (Protected Resources) SHOULD NOT include offline_access in ... scopes_supported"; registro por CIMD, pre-registro o DCR (deprecado); validación de `iss` según tabla RFC 9207. — [DOC] https://modelcontextprotocol.io/specification/draft/basic/authorization
- Resumen de terceros de los 6 SEPs de auth de julio 2026: SEP-2468 (iss), SEP-837 (application_type), SEP-2352 (aislamiento por issuer), SEP-2207 (refresh via `offline_access`), SEP-2350 (step-up de scopes), SEP-2351 (discovery). — [PRENSA] https://www.descope.com/blog/post/july-2026-mcp-revision ; https://dev.to/tigeraio/mcps-auth-hardening-what-the-six-new-oauth-seps-fix-and-what-they-still-dont-2g0c

**Tool annotations (2025-06-18):** las tools llevan `annotations` opcionales; "clients MUST consider tool annotations to be untrusted unless they come from trusted servers"; "there SHOULD always be a human in the loop with the ability to deny tool invocations"; servidores MUST validar inputs, controlar acceso, rate-limit; clientes SHOULD pedir confirmación en operaciones sensibles, mostrar inputs, loguear uso. — [DOC] https://modelcontextprotocol.io/specification/2025-06-18/server/tools . Claude Code usa `readOnlyHint` (ejecuta en paralelo y puede repetir la llamada tras corte de conexión) e `idempotentHint` (puede repetir), y define el `_meta["anthropic/requiresUserInteraction"]: true` para forzar el prompt completo de permiso aunque haya reglas allow. — [DOC] https://code.claude.com/docs/en/mcp

**Elicitation (2025-06-18):** `elicitation/create` con `requestedSchema` plano (string/number/boolean/enum), respuestas `accept|decline|cancel`; "Servers MUST NOT use elicitation to request sensitive information". — [DOC] https://modelcontextprotocol.io/specification/2025-06-18/client/elicitation . Claude Code soporta modo formulario y **modo URL** ("Claude Code asks whether to open a link in your browser. Servers use this mode for a flow that finishes outside the terminal, such as sign-in"), declara `elicitation: {form: {}, url: {}}` en conexiones 2026-07-28 y, desde v2.1.287, en servidores http/sse/stdio/ws de la configuración del usuario; en sesiones no interactivas pide cancelar la task; hay hook `Elicitation` para auto-responder. — [DOC] https://code.claude.com/docs/en/mcp

**Soporte en clientes:**
- **Claude (claude.ai, Desktop, mobile, Claude Code, Cowork):** tipos `oauth_dcr`, `oauth_cimd`, `oauth_anthropic_creds`, `custom_connection`, `static_headers` (beta), `none`; "A 401 is required to start sign-in"; usa solo el primer `authorization_servers`; CIMD solo si el AS anuncia `client_id_metadata_document_supported: true` y `none`; PKCE S256 siempre; "If you don't [send scope in WWW-Authenticate], Claude requests the scopes your protected resource metadata advertises in scopes_supported. Claude also appends offline_access when your authorization server metadata lists it"; callback de apps hosted `https://claude.ai/api/mcp/auth_callback`; Claude Code usa loopback RFC 8252 en puerto efímero (`http://localhost:<port>/callback` y `127.0.0.1`), con su propio CIMD en `https://claude.ai/oauth/claude-code-client-metadata`; timeouts 10 s (discovery/registro/token) y 30 s (refresh); egress Anthropic `160.79.104.0/21`; `client_credentials` no soportado. — [DOC] https://claude.com/docs/connectors/building/authentication

Issues conocidos: intenta DCR aunque haya client id configurado (#67258) y reutiliza registros DCR cacheados aunque el servidor los haya purgado (#84614, v2.1.223). — [PRENSA/issues] https://github.com/anthropics/claude-code/issues/67258 ; https://claudeissues.com/issue/84614-mcp-oauth-stale-dynamic-client-registration-replayed-forever-after-server-prunes

### Inferences
- Para belo: como bifrost no anuncia `client_id_metadata_document_supported`, todos los clientes caen en DCR (que belo soporta, verificado). Hoy belo, según la guía citada por el solicitante, devuelve el link en el resultado de la tool; con MRTR (2026-07-28) ese flujo se modela como `input_required` + reintento.

## Pregunta 5: Consideraciones de seguridad para un MCP bancario

### Takeaway
El spec y las guías de seguridad de MCP cubren confused deputy, token passthrough, SSRF en discovery, session hijacking, validación de URLs de autorización y minimización de scopes; para un MCP bancario como belo, el diseño "token que solo propone + aprobación fuera de banda" es la mitigación principal contra prompt injection, y las piezas faltantes visibles desde afuera son `scope=` en el 401, `iss` en las respuestas, permisos por agente y límites de gasto (ambos "coming soon").

### Cited Findings
- **Confused deputy:** ataque sobre MCP proxy con client ID estático + DCR + cookie de consentimiento; "MCP proxy servers MUST implement per-client consent"; registro de `client_id` aprobados por usuario; consent UI que identifique al cliente, scopes y `redirect_uri`; cookies `__Host-`, `Secure`, `HttpOnly`, `SameSite=Lax`; `redirect_uri` con match exacto; `state` aleatorio, de un solo uso, ~10 min, guardado solo después del consentimiento. — [DOC] https://modelcontextprotocol.io/specification/2025-06-18/basic/security_best_practices
- **Token passthrough:** "MCP servers MUST NOT accept any tokens that were not explicitly issued for the MCP server"; el token hacia la API upstream es otro token. — [DOC] ídem
- **SSRF en discovery:** las URLs de `resource_metadata`, `authorization_servers`, `token_endpoint` vienen del servidor y pueden apuntar a `169.254.169.254`; clientes server-side SHOULD exigir HTTPS, bloquear rangos privados (RFC 9728 §7.7) y usar egress proxy (Smokescreen). — [DOC] ídem
- **Session hijacking:** "MCP servers that implement authorization MUST verify all inbound requests. MCP Servers MUST NOT use sessions for authentication"; IDs de sesión aleatorios y ligados a `<user_id>:<session_id>`. — [DOC] ídem
- **Validación de URL de autorización:** clientes MUST permitir solo `http(s)` (http solo loopback), rechazar `javascript:`/`data:`/`file:`, no abrir URLs vía shell. — [DOC] ídem
- **Scope minimization:** evitar publicar todos los scopes en `scopes_supported`, usar challenges `scope=` incrementales, loguear elevaciones; "Common Mistakes: Publishing all possible scopes in scopes_supported; Using wildcard or omnibus scopes". — [DOC] ídem
- **Audience binding:** servidores "MUST only accept tokens specifically intended for themselves and MUST reject tokens that do not include them in the audience claim"; "Authorization servers SHOULD issue short-lived access tokens"; "For public clients, authorization servers MUST rotate refresh tokens". — [DOC] https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization
- **Prompt injection y confirmación humana:** Stripe: "Turn on your MCP client's tool-approval setting so you can review tool calls before they run, and exercise caution when using the Stripe MCP with other servers to avoid prompt injection attacks"; además logs de llamadas MCP en Workbench y revocación de sesiones OAuth por usuario/admin. — [DOC] https://docs.stripe.com/mcp
- **Tools:** "clients MUST consider tool annotations to be untrusted unless they come from trusted servers"; servidores MUST rate-limit y validar inputs; clientes SHOULD loguear para auditoría. — [DOC] https://modelcontextprotocol.io/specification/2025-06-18/server/tools
- **Elicitation:** "Servers MUST NOT request sensitive information through elicitation" (es decir, nunca pedir PIN/2FA/contraseña por elicitation; eso justifica el link de aprobación fuera de banda). — [DOC] https://modelcontextprotocol.io/specification/2025-06-18/client/elicitation
- **Belvo** describe su control como "consented, identity-bound credential ... each call is logged and auditable"; **Mercury** anuncia tokens de corta vida, revocación desde el dashboard, IP allow-listing y separación read/write. — [PRENSA] https://thepaypers.com/fintech/news/belvo-launches-mcp-servers-for-agentic-open-finance ; https://docs.mercury.com/docs/security-best-practices
- **Claude** aconseja a los servidores mostrar el hostname del redirect en la pantalla de consentimiento y advertir cuando solo hay redirects loopback ("any local process can bind a port and claim to be the client"), y publica su rango de egress `160.79.104.0/21` para allowlists. — [DOC] https://claude.com/docs/connectors/building/authentication
- **Geofencing de belo (dato del solicitante):** bloqueo de requests desde servidores cloud durante el hackathon. Verificado parcialmente: los `.well-known` y `/oauth/register` responden desde una IP residencial; no probé desde una nube. — [SONDEO]

### Inferences
- Riesgos concretos para belo visibles desde afuera: (1) el 401 no manda `scope=`, así que los clientes piden los 16 scopes y el único control es la pantalla de consentimiento; (2) `scopes_supported` publica el catálogo completo (exactamente el "common mistake" del spec); (3) DCR abierto sin aprobación significa que cualquier software puede registrarse como cliente — la seguridad descansa en el consentimiento del usuario y en el link de aprobación por operación; (4) no hay `iss` anunciado (mix-up attack teórico si algún día coexisten varios AS); (5) `end-users:write` y `cards:write` en una cuenta empresa son scopes de alto impacto que conviene no pedir desde un agente de consulta.
- El link de aprobación de 15 minutos mitiga prompt injection: aunque un documento malicioso haga que el agente "cotice" una transferencia, nada se mueve sin un click humano en un canal distinto al chat. El residuo es la ingeniería social (que el humano apruebe sin leer): por eso el link debería mostrar monto, destino y origen de la instrucción.
- Para un agente que corre en una máquina local (hackathon), el bloqueo de IPs cloud reduce el riesgo de agentes desatendidos en servidores, pero obliga a que el bot de WhatsApp/Telegram corra en la laptop (túnel o polling) o a que la parte que habla con belo sea local.

### Gaps
- Rate limits, auditoría visible al usuario, revocación de clientes DCR y vida de los tokens de bifrost: sin fuente.
- Si belo valida `Origin` / usa `Mcp-Session-Id`: no observable sin token.

## Pregunta 6: Piezas prácticas para un proyecto de hackathon con el MCP de belo desde un agente local (SDKs MCP, Claude Agent SDK, OAuth local, pasar el link por WhatsApp/Telegram)

### Takeaway
Hay dos caminos: (a) usar Claude Code / Claude Desktop / Cursor / Codex como cliente MCP (hacen el OAuth DCR+PKCE solos y muestran el link de aprobación que devuelve la tool), o (b) construir un agente propio con el SDK MCP (TypeScript v2 `@modelcontextprotocol/client` o Python `mcp`), que implementan `OAuthClientProvider` con DCR, PKCE, loopback redirect y storage de tokens, y combinarlo con el Claude Agent SDK pasando el access token por `headers` (el Agent SDK no corre el flujo OAuth) y con `canUseTool` para interceptar las tools de escritura y reenviar la aprobación por WhatsApp/Telegram.

### Cited Findings
**SDK MCP TypeScript v2 (`@modelcontextprotocol/client`, spec 2026-07-28; v1.x en rama aparte):**
- Se implementa `OAuthClientProvider` y se pasa como `authProvider` a `new StreamableHTTPClientTransport(url, { authProvider })`. Métodos: `redirectToAuthorization(url)`, `tokens()`/`saveTokens(tokens)`, `clientInformation(ctx?)`/`saveClientInformation(info, ctx?)` (claveadas por `ctx.issuer`, es decir SEP-2352), `clientMetadata` (`client_name`, `redirect_uris`, `application_type`), `saveCodeVerifier`/`codeVerifier` (PKCE), `state()`, `saveDiscoveryState`/`discoveryState`, opcionales `validateResourceURL`, `scopeForRefresh`. Flujo CLI: `redirectUrl: 'http://localhost:8090/callback'` con `application_type: 'native'`; `client.connect(transport)` lanza `UnauthorizedError`; la app recibe el callback, valida `state` contra `provider.lastState`, llama `transport.finishAuth(params)` (valida `iss`, canjea el code, guarda tokens) y reconecta con un transporte nuevo. Errores: `UnauthorizedError`, `IssuerMismatchError`, `OAuthError`. — [DOC] https://ts.sdk.modelcontextprotocol.io/v2/clients/oauth.html ; https://github.com/modelcontextprotocol/typescript-sdk
**SDK MCP Python (`pip install "mcp[cli]"`):**
- `OAuthClientProvider(server_url, client_metadata=OAuthClientMetadata(client_name, redirect_uris, scope), storage=TokenStorage, redirect_handler, callback_handler)` es un `httpx2.Auth`; se monta en `httpx2.AsyncClient` y se pasa a `streamable_http_client(url, http_client=...)`; `TokenStorage` es un Protocol con `get_tokens/set_tokens/get_client_info/set_client_info`; el provider hace discovery (WWW-Authenticate → PRM → AS metadata), DCR si no hay `client_info`, PKCE y `state`, canje y refresh; `callback_handler` devuelve `AuthorizationCodeResult(code, state, iss)`; CIMD opcional con `client_metadata_url=` (solo si el AS anuncia `client_id_metadata_document_supported`, si no cae a DCR); errores `OAuthFlowError`/`OAuthRegistrationError`/`OAuthTokenError`; ejemplos en `examples/clients/simple-auth-client/`. — [DOC] https://py.sdk.modelcontextprotocol.io/client/oauth-clients/
**Claude Agent SDK (TS `@anthropic-ai/claude-agent-sdk`, Python `claude_agent_sdk`):**
- Servidores MCP en `options.mcpServers` con `{ type: "http", url, headers }` (o `.mcp.json`); tools se nombran `mcp__<server>__<tool>` y deben autorizarse con `allowedTools` (p. ej. `mcp__belo__*` o solo las de lectura); "The SDK doesn't open a browser or run an interactive OAuth flow. When a configured server returns an authorization challenge and Claude Code has no token to send, the SDK reports the server as `needs-auth`"; soluciones: pasar `Authorization: Bearer <token>` en `headers` tras completar OAuth en tu app, o hacer login desde una sesión interactiva de Claude Code en la misma máquina; `createSdkMcpServer()` permite tools in-process. — [DOC] https://code.claude.com/docs/en/agent-sdk/mcp
- Permisos: orden hooks → deny → ask → modo → allow → `canUseTool`; `canUseTool` recibe las llamadas no resueltas y decide allow/deny; "Auto-approved tools never reach canUseTool"; MCP tools con `_meta["anthropic/requiresUserInteraction"]` siempre caen al callback aunque haya allow; modos `default`, `dontAsk`, `acceptEdits`, `bypassPermissions`, `plan`, `auto`; `PreToolUse` hooks corren siempre, incluso en `bypassPermissions`; `setPermissionMode()` en caliente. — [DOC] https://code.claude.com/docs/en/agent-sdk/permissions
- Claude Code (cliente) soporta elicitation en modo URL (abre el link en el navegador) y el hook `Elicitation` para auto-responder; en no interactivo cancela. — [DOC] https://code.claude.com/docs/en/mcp
**OAuth para agentes locales:**
- El spec exige redirect `localhost` o HTTPS y PKCE; Claude Code usa loopback RFC 8252 con puerto efímero y declara `http://localhost/callback` y `http://127.0.0.1/callback` (match ignorando puerto). — [DOC] https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization ; https://claude.com/docs/connectors/building/authentication
- bifrost aceptó `redirect_uris: ["http://localhost:1/cb"]` en DCR (201), así que el loopback funciona con belo. — [SONDEO] https://bifrost.belo.app/oauth/register
- Claude Code: `claude mcp add --transport http belo https://b2b.belo.app/mcp` y luego `/mcp` o `claude mcp login belo` (`--no-browser` imprime la URL); fijar scopes con `oauth.scopes`. — [DOC] https://code.claude.com/docs/en/mcp
**Entregar el link de aprobación por WhatsApp/Telegram:**
- WhatsApp Cloud API: `POST https://graph.facebook.com/<API_VERSION>/<PHONE_NUMBER_ID>/messages` con `Authorization: Bearer <token>`, body `{"messaging_product":"whatsapp","recipient_type":"individual","to":"+549...","type":"text","text":{"body":"...url...","preview_url":true}}`; hasta 4096 caracteres; el cliente hiperlinkea la URL y puede previsualizar la primera. — [DOC] https://developers.facebook.com/docs/whatsapp/cloud-api/messages/text-messages
- Telegram Bot API: el bot recibe updates por `getUpdates` (long polling, `timeout`, `offset`, `limit` 1-100) o `setWebhook` (HTTPS, `secret_token` en header `X-Telegram-Bot-Api-Secret-Token`); los updates se guardan hasta 24 h; `sendMessage` admite `reply_markup` con botones inline (la sección específica no se pudo leer por tamaño de la página). — [DOC] https://core.telegram.org/bots/api
- Prerrequisito de los T&C del hackathon: la demo "se ejecuta en vivo desde los equipos de los propios Participantes" y el Sandbox usa fondos ficticios; está prohibido conectar a producción. — [DOC legal] https://agentic.belo.app/documents/tyc-belo-agentic-banking-hackathon-2026.pdf

### Inferences
- Arquitectura mínima recomendable para el hackathon: proceso local (laptop, cumple el bloqueo de IPs cloud) con (1) cliente MCP propio o Claude Agent SDK con token en `headers`; (2) OAuth una sola vez con loopback y refresh con `offline_access` (bifrost lo anuncia); (3) `allowedTools` solo para lectura y `canUseTool` para interceptar `transfers:initiate`/`swaps:execute`/`pix:write`, de modo que el bot muestre la cotización en el chat y mande el link de belo al usuario; (4) Telegram con long polling evita exponer un webhook público desde la laptop (WhatsApp Cloud API exige webhook HTTPS para recibir, así que requiere túnel tipo ngrok/cloudflared, y la IP de belo seguiría siendo la local porque el túnel solo entra). (5) Como el link vence a los 15 minutos, el bot debe pedir el link solo cuando el usuario confirma en el chat, no al cotizar.
- Si se usa Claude Code/Desktop directamente, la aprobación ocurre con el link que devuelve la tool y el usuario lo abre; no se necesita código, pero no hay canal WhatsApp/Telegram.
- Con el SDK TS v2 (spec 2026-07-28, sin `initialize`/sesiones) existe riesgo de incompatibilidad si el servidor de belo es un SDK v1 con `Mcp-Session-Id`; el SDK v1.x (rama separada) o el SDK Python (que negocia versiones) son opciones más seguras hasta verificar.

### Gaps
- No se verificó el flujo OAuth completo contra bifrost (requiere cuenta belo y login con Google); se desconoce la pantalla de consentimiento real y la vida de los tokens.
- No hay evidencia pública de cómo la tool de belo devuelve el link de aprobación (campo del resultado, `resource_link`, elicitation URL o texto): dato de la guía privada del hackathon.
- Versión exacta del SDK TS v2 y compatibilidad hacia atrás con servidores 2025-06-18: no leída en detalle.
